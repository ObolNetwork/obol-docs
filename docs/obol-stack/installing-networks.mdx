# Installing networks

The Obol Stack supports installing multiple blockchain networks on your local Kubernetes cluster. Each network installation creates a unique deployment with its own namespace, allowing you to run multiple instances simultaneously.

## Available networks

List your installed deployments, the network types you can install, and any remote RPCs:

```shell
obol network list
```

From Obol Stack v0.16, `obol network list` shows each installed deployment with its network, execution and consensus clients, and mode.

Currently supported networks:

| Network | Description |
| --- | --- |
| **ethereum** | Full Ethereum node (execution + consensus clients) |
| **aztec** | Aztec Layer 2 sequencer node |

## Network installation workflow

Installing a network follows a two-step process:

1. **Install** - Generate configuration and save to disk
2. **Sync** - Deploy the configuration to the cluster

This separation allows you to review and modify configuration before deployment.

### Install command

```shell
obol network install <network> [flags]
```

This creates a deployment directory at `~/.config/obol/networks/<network>/<id>/` containing:

* `values.yaml` - Configuration values (editable)
* `helmfile.yaml` - Deployment definition

### Sync command

```shell
# Auto-selects if only one deployment exists
obol network sync

# By type (auto-selects if only one ethereum deployment)
obol network sync ethereum

# By full identifier
obol network sync <network>/<id>

# Sync all deployments at once
obol network sync --all
```

This deploys the configuration to your Kubernetes cluster using Helmfile.

### Delete command

```shell
# Auto-selects if only one deployment exists
obol network delete

# By type (auto-selects if only one of that type)
obol network delete ethereum

# By full identifier
obol network delete <network>/<id>
```

This removes both the Kubernetes resources and local configuration.

## Ethereum network

Deploy a full Ethereum node with configurable execution and consensus clients.

### Configuration options

| Flag | Description | Options | Default |
| --- | --- | --- | --- |
| `--id` | Deployment identifier | Any string | Network name (e.g. `mainnet`), then petname |
| `--network` | Ethereum network | mainnet, sepolia, hoodi | mainnet |
| `--execution-client` | Execution layer client | reth, geth, nethermind, besu, erigon | reth |
| `--consensus-client` | Consensus layer client | lighthouse, prysm, teku, nimbus, lodestar, grandine, silver¹ | lighthouse |
| `--mode` | Pruning mode | full, archive | full |
| `--since` | Lower bound for archive history (requires `--mode=archive`) | fork name, duration, block number, `genesis`/`all` | (interactive picker on TTY; `all` on non-TTY) |
| `--execution-memory` | Memory limit for the execution client | a size, e.g. `16Gi` | sized per network, mode and client |
| `--consensus-memory` | Memory limit for the consensus client | a size, e.g. `8Gi` | sized per network and client |

¹ [Silver](https://github.com/gattaca-com/silver) is in alpha. Try it on a testnet first. It needs Obol Stack v0.18.0 or later. From v0.19.0 it runs on amd64 and arm64 machines, including Apple Silicon; v0.18 ran it on amd64 only. Moving a Silver node from v0.18 to v0.19 needs a fresh checkpoint sync, see [Upgrades and your own image tags](#upgrades-and-your-own-image-tags).

### Client versions

Each Obol Stack release pins one version of every client. `obol network sync` moves a node to the versions of the `obol` you run.

| Execution client | v0.19.0 | Consensus client | v0.19.0 |
| --- | --- | --- | --- |
| reth (default) | v2.11.0 | lighthouse (default) | v8.3.3 |
| geth | v1.17.10 | prysm | v7.3.2 |
| nethermind | 2.3.0-rc | teku | 26.11.0 |
| besu | 26.11.3 | nimbus | v26.10.2 |
| erigon | v3.8.2 | lodestar | v1.51.0 |
| | | grandine | 2.0.6 |
| | | silver | v0.1.0-alpha.23 |

Nethermind is on a release candidate because 2.2.2 doesn't know the Sepolia Amsterdam fork, which activated on 2026-10-06.

:::warning[Hoodi's Gloas/Amsterdam fork]
Hoodi's Gloas/Amsterdam fork is planned for epoch 143616, at 2026-12-15 19:12:24 UTC. In Obol Stack v0.19.0 only Besu 26.11.3 and Silver alpha.23 schedule it. The other clients, including the default reth and Lighthouse, need a later Obol Stack release. If you run a Hoodi node, upgrade the Obol Stack and run `obol network sync` before the fork, or your node stops following Hoodi.
:::

Full Ethereum nodes require significant resources. Mainnet execution clients need 1+ TB of storage and can take days to sync. Consider using testnets for development.

### Memory

From v0.18.0, each client gets a memory request (what the cluster reserves for it) and a memory limit (where it is restarted). Both are sized per network, mode and client, so you normally set nothing. Each client is also told its limit, so it keeps its own caches and heap under it:
- Geth, Erigon and Prysm get `GOMEMLIMIT`.
- Teku, Besu and Lodestar get heap sizes.
- Nethermind gets its memory hint.
- reth gets its cache size.

Hoodi's beacon nodes get the same limits as mainnet's, because Hoodi has as many validators as mainnet. No limit is larger than the cluster itself.

`--execution-memory` and `--consensus-memory` set a client's **limit**. Before v0.18.0 they set the request. To change one later, edit `executionMemory` / `consensusMemory` in the deployment's `values.yaml` and run `obol network sync`. Sync warns when a value is below the default limit, since the client may then be restarted for running out of memory.

`obol network install` and `obol network sync` warn when the cluster's memory requests won't fit. If that happens:
- **Stop a node you don't need:** `obol network stop ethereum/<id>`.
- **Or lower a client's memory**, accepting that it may be restarted more often.

After upgrading the Obol Stack, run `obol network sync` for each node. Its clients restart once to pick up new requests, limits and versions; their data is kept.

The cluster itself has a memory cap; see [Quickstart](./quickstart.mdx#memory).

### MEV

The Obol Stack doesn't run MEV-boost. Until the Gloas fork the beacon node builds blocks locally; from Gloas, builder bids arrive in-protocol over the p2p network, so relays and MEV-boost no longer apply. Validators that use this node, such as an [Obol DV pod](run-a-dv.md), keep builder proposals off (`charon.builderApi=false`).

### Archive nodes and bounded history (`--since`)

Pruned full nodes are sufficient for everyday RPC use, but they cannot serve historical state. If you plan to **index events, run historical `eth_call`, build a block explorer, or back a query service with a specific app's history**, you need an archive node — and you almost certainly do not need it all the way back to genesis.

`--mode=archive` switches reth to archive mode. `--since` bounds the archive at a known starting point, so you only carry the history you actually need.

```shell
# Archive back to the Cancun hardfork (~800 GB on mainnet)
obol network install ethereum --network=mainnet --mode=archive --since=cancun

# Archive of the last 365 days (~600 GB)
obol network install ethereum --network=mainnet --mode=archive --since=365d

# Archive from a specific block forward (e.g. the block at which your DeFi app was deployed)
obol network install ethereum --network=mainnet --mode=archive --since=22500000

# Full archive from genesis (~4 TB+ on mainnet)
obol network install ethereum --network=mainnet --mode=archive --since=all
```

Accepted `--since` values:

| Form | Example | Meaning |
| --- | --- | --- |
| EL fork name | `merge`, `shanghai`, `cancun`, `prague`, `osaka` | Prune state before that mainnet hardfork. |
| Duration | `365d`, `1y`, `6mo` | Keep approximately the last N blocks (~12s slot rate). |
| Block number | `22500000` | Prune state before that block. |
| `genesis` / `all` | `all` | Full archive from genesis. |

:::info
Fork-name presets reference **mainnet** block numbers. On testnets, use a raw block number or a duration.
:::

When `--mode=archive` is set without `--since` on a TTY, the installer shows an interactive picker. On non-TTY (scripts, CI), the default is `all`. `--since` is currently fine-tuned for **reth**; other execution clients fall back to their chart-default pruning behavior with a warning.

This pairs naturally with [Selling agent services](selling-services.md) — once your archive node has synced from the block at which your target application was deployed, you have a defensible data set that no public RPC will serve, and you can wrap it as a paid endpoint or a specialized agent.

### Check sync status

From Obol Stack v0.16, `obol network status` shows each node's sync state:

```shell
obol network status                     # the RPC gateway and every installed node
obol network status ethereum/<id>       # one node
obol -o json network status ethereum/<id>
```

For each Ethereum deployment it prints the pods, the execution client's sync state, head block, peers and version, the beacon node's sync distance, peers and version, and a one-line verdict such as `synced`, `syncing` (with progress), `el_offline` or `unreachable`. Wait for `synced` before you point validators at the node.

From v0.19.0, a node stopped with `obol network stop` shows since when it has been down, and roughly how many slots behind it will be when you start it again.

The node's APIs aren't published on `obol.stack`; they are only reachable inside the cluster, at `http://ethereum-execution.ethereum-<id>.svc.cluster.local:8545` and `http://ethereum-beacon.ethereum-<id>.svc.cluster.local:5052`. To query them from your machine (v0.19.0 or later):

```shell
obol network expose ethereum/<id> --execution &
curl -s http://127.0.0.1:8545 -X POST -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'
```

On older versions, port-forward instead: `obol kubectl -n ethereum-<id> port-forward svc/ethereum-execution 8545:8545 &`.

### Use the node from Docker containers

`obol network expose` (v0.19.0 or later) forwards a node's beacon API (`--beacon`, port 5052) and execution JSON-RPC (`--execution`, port 8545) to a local address, so Docker containers on the same machine can use it: a Charon node, a test validator client. With neither flag it forwards both. It runs in the foreground until Ctrl-C, checks the APIs every 15 seconds and reconnects when a pod restarts. It never exposes the engine API.

```shell
# Docker Desktop: containers reach 127.0.0.1 as host.docker.internal
obol network expose ethereum/<id> --beacon
#   charon --beacon-node-endpoints=http://host.docker.internal:5052

# Linux: bind the docker0 bridge address and use it from the container
obol network expose ethereum/<id> --beacon --bind 172.17.0.1 --beacon-port 15052
#   charon --beacon-node-endpoints=http://172.17.0.1:15052
```

`--bind` accepts loopback and private addresses. Binding anything else, including `0.0.0.0`, needs `--allow-public`.

:::danger
The node APIs have no authentication. Don't use `--allow-public` unless a firewall keeps the port off the internet.
:::

To look at the pods and logs directly:

```shell
# View pod status
obol kubectl get pods -n ethereum-<id>

# Check execution client logs
obol kubectl logs -n ethereum-<id> -l app=execution -f

# Check consensus client logs
obol kubectl logs -n ethereum-<id> -l app=consensus -f
```

## Aztec network

Deploy an Aztec Layer 2 sequencer node for the privacy-focused Ethereum rollup.

### Configuration options

| Flag | Description | Options | Default |
| --- | --- | --- | --- |
| `--id` | Deployment identifier | Any string | Network name (e.g. `mainnet`), then petname |
| `--network` | Aztec network | mainnet | mainnet |
| `--attester-private-key` | Attester private key (hex) | Required | None |
| `--l1-execution-url` | L1 execution RPC URL | URL | ERPC endpoint |
| `--l1-consensus-url` | L1 consensus RPC URL | URL | Public endpoint |

### Example

```shell
obol network install aztec \
  --attester-private-key=<YOUR_PRIVATE_KEY> \
  --l1-execution-url=https://geth-prysm-mainnet-1.gcp.obol.tech/ \
  --l1-consensus-url=https://prysm-geth-mainnet-1.gcp.obol.tech/
```

Deploy to the cluster:

```shell
obol network sync aztec/<id>
```

:::info
You can use your own Ethereum node endpoints or the in-cluster ERPC endpoint by changing the L1 URL flags.
:::

### Resource requirements

| Resource | Request | Limit |
| --- | --- | --- |
| **CPU** | 4 cores | 8 cores |
| **Memory** | 16 GB | 32 GB |
| **Storage** | 1 TB | - |

:::warning
Ensure your machine has sufficient resources before deploying an Aztec node.
:::

## Managing deployments

### View deployment status

```shell
obol network list                       # installed deployments (v0.16+)
obol network status                     # live sync status (v0.16+)
obol kubectl get namespaces | grep -E "ethereum|aztec"
```

### Modify configuration

```shell
$EDITOR ~/.config/obol/networks/<network>/<id>/values.yaml

# Re-deploy (auto-selects if only one deployment, otherwise specify)
obol network sync <network>/<id>
```

### Upgrades and your own image tags {#upgrades-and-your-own-image-tags}

`obol network sync` renders each deployment from the network files built into your `obol`, so a new `obol` brings new client versions and template fixes. After upgrading the Obol Stack, run `obol network sync` for each node.

From v0.19.0, sync checks the running images first:

* **Hand changes are reverted.** If you changed a client's image in the cluster (`obol kubectl set image …`), sync names the image it is about to replace. To keep your own settings, put them in `overrides.yaml` next to the deployment's `values.yaml` (`~/.config/obol/networks/ethereum/<id>/overrides.yaml`). It is merged last into the node's chart values and kept across upgrades:

  ```yaml
  # Pin Silver to a specific release
  silver:
    image:
      tag: v0.1.0-alpha.23
  ```

* **Some upgrades can't reuse the existing data.** Silver changed its storage format in v0.1.0-alpha.18, and Obol Stack v0.18 ran alpha.13, so every Silver node needs a fresh checkpoint sync when it moves to v0.19. Sync detects this, prints the steps and asks first; without a terminal it needs `--yes`. It never deletes data itself:

  ```shell
  obol network stop ethereum/<id>
  obol network sync ethereum/<id> --yes   # new image, still stopped
  sudo find ~/.local/share/obol/ethereum-<id>/consensus-silver-<network> -mindepth 1 -delete
  obol network start ethereum/<id>        # Silver checkpoint-syncs from scratch
  ```

  Sync prints the exact data path for your deployment. Only the beacon node's data is removed; the execution client keeps its data.

:::note
A StatefulSet doesn't roll a pod that never became ready, so a client that was crash-looping before the upgrade would keep the old spec. From v0.19.0, `obol network sync` handles this: after up to a minute it deletes such pods (only ones that were never ready) so they are recreated from the new spec, and their data is kept. If you applied a change some other way, delete the pod yourself, for example `obol kubectl -n ethereum-<id> delete pod ethereum-beacon-0`.
:::

`obol doctor` warns when a node's client keeps restarting (three or more restarts, the last one within 24 hours) and prints the `obol kubectl … logs --previous` command that shows why.

### Silver

Silver is an alpha client. Notes for running it in the Obol Stack (v0.19.0):

* Its beacon API only answers requests whose `Host` is an IP address, `localhost`, or a name the Stack configures: the deployment's `ethereum-beacon` service names and `host.docker.internal`. Other names get `403 host not allowed`. To allow more, set `silver.config` in `overrides.yaml`. It replaces the Stack's whole block, so repeat its lines:

  ```yaml
  silver:
    config: |
      beacon_api_allowed_hosts = ["ethereum-beacon", "ethereum-beacon.ethereum-<id>", "ethereum-beacon.ethereum-<id>.svc", "ethereum-beacon.ethereum-<id>.svc.cluster.local", "host.docker.internal", "my-name"]
      metrics.enabled = true
      metrics.bind = "0.0.0.0:5054"
  ```

* Its metrics are on port 5054, not on the API port. The Stack's Prometheus scrapes them there.
* If Silver misbehaves, run a second node with the default consensus client next to it. It gets its own namespace and data:

  ```shell
  obol network install ethereum --network hoodi --consensus-client lighthouse --id hoodi-lighthouse
  obol network sync ethereum/hoodi-lighthouse
  ```

  Then point whatever used the Silver node, such as a dv-pod's `charon.beaconNodeEndpoints`, at `ethereum-beacon.ethereum-hoodi-lighthouse`. On Hoodi, Lighthouse in v0.19.0 doesn't schedule the Gloas fork (see [Client versions](#client-versions)).

### Delete a deployment

```shell
# Auto-selects if only one deployment exists
obol network delete

# Or specify explicitly
obol network delete <network>/<id>
```

:::warning
Deletion is permanent. All blockchain data stored in the deployment will be lost.
:::

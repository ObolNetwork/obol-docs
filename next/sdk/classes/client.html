Client

Defined in: index.ts:185

Primary entrypoint for the Obol SDK. Use this class to create, manage, and activate Distributed Validators via the Obol API.

All operations are namespaced under the client instance:

  • client.incentives.* – claim and query Obol incentives
  • client.exit.* – validate and recombine voluntary exit signatures
  • client.splits.* – deploy OVM / SplitV2 reward-splitting contracts
  • client.eoa.* – EOA withdrawals and batch deposits

Cluster lifecycle helpers live directly on the client:

  • Client.hasAcceptedTerms
  • Client.acceptObolLatestTermsAndConditions
  • Client.createClusterDefinition
  • Client.acceptClusterDefinition
  • Client.getClusterDefinition
  • Client.getClusterLock
  • Client.getClusterLockByHash
  • Client.getDepositData
  • Client.createObolRewardsSplit
  • Client.createObolTotalSplit
  • Client.getOWRTranches

Supported networks (by chainId): Mainnet (1) and Hoodi (560048), plus Gnosis (100) and Sepolia (11155111) for cluster definitions and locks only (no splitter contracts; not recommended for new clusters). Any other chainId throws UnsupportedChainError from the constructor.

Example​

import { Client } from "@obolnetwork/obol-sdk";
import { Wallet } from "ethers";

const signer = new Wallet(process.env.PRIVATE_KEY!);
const client = new Client({ chainId: 560048 }, signer);

// 1. Accept terms (required once before creating/updating data)
await client.acceptObolLatestTermsAndConditions();

// 2. Create a cluster definition
const configHash = await client.createClusterDefinition({
  name: "my-cluster",
  operators: [{ address: "0x..." }],
  validators: [{
    fee_recipient_address: "0x...",
    withdrawal_address: "0x...",
  }],
});

// 3. Retrieve the definition
const def = await client.getClusterDefinition(configHash);

acceptObolLatestTermsAndConditions()​

acceptObolLatestTermsAndConditions(options?): Promise<string>

Defined in: index.ts:343

Accepts the latest Obol terms and conditions.

Must be called once before any write operation (createClusterDefinition, acceptClusterDefinition, etc.).

  • Requires a signer to be provided at client construction.
  • Signs an EIP-712 typed-data message; no on-chain transaction is sent.
  • Not idempotent by default: calling it again after acceptance throws a ConflictError. Pass { ifNotAccepted: true } to first check with Client.hasAcceptedTerms and return without signing if the signer has already accepted.

Parameters​

ParameterTypeDescription
options?{ ifNotAccepted?: boolean; }Optional settings.
options.ifNotAccepted?booleanWhen true, skip signing and return TERMS_ACCEPTED_MSG if the signer has already accepted the terms.

Returns​

Promise<string>

A success message string from the Obol API.

Throws​

If no signer was provided to the client.

Throws​

If the terms were already accepted by this address (only when ifNotAccepted is not set).

Example​

const message = await client.acceptObolLatestTermsAndConditions({
  ifNotAccepted: true,
});
console.log(message); // "successful authorization"

createObolRewardsSplit()​

createObolRewardsSplit(rewardsSplitPayload): Promise<ClusterValidator>

Defined in: index.ts:437

Deploys an Optimistic Withdrawal Recipient (OWR) and a Splitter Proxy contract.

Use this when the principal goes to a single address and only rewards are split among recipients. For splitting both principal and rewards, see Client.createObolTotalSplit.

  • Requires a signer with ETH to pay deployment gas.
  • Sends one or more on-chain transactions (irreversible).
  • Automatically appends the Obol Retroactive Funding (RAF) recipient at the configured percentage (default 1%).
  • Only supported on Mainnet (1) and Hoodi (560048).
  • With a controllerAddress (a mutable split), the splitter is deployed in its own transaction first and the OWR is created with its address in a second one, since a mutable split's address cannot be predicted. Without one, an immutable splitter and the OWR are deployed together.

Parameters​

ParameterTypeDescription
rewardsSplitPayloadRewardsSplitPayloadConfiguration for the OWR and splitter deployment.

Returns​

Promise<ClusterValidator>

The deployed OWR address as withdrawal_address and the splitter proxy address as fee_recipient_address.

Throws​

If no signer was provided.

Throws​

If the signer is connected to a different chain.

Throws​

If the chain does not support splitters.

Example​

const { withdrawal_address, fee_recipient_address } =
  await client.createObolRewardsSplit({
    splitRecipients: [
      { account: "0xOperator1...", percentAllocation: 50 },
      { account: "0xOperator2...", percentAllocation: 49 },
    ],
    principalRecipient: "0xPrincipalAddress...",
    etherAmount: 32,
  });

Deprecated​

For new clusters use ObolSplits.createValidatorManagerAndRewardsSplit. An OWR cannot make EIP-7002 withdrawal requests, so getting the stake back depends on pre-signed exits. Reading existing OWRs (Client.getOWRTranches) is unaffected.

createObolTotalSplit()​

createObolTotalSplit(totalSplitPayload): Promise<ClusterValidator>

Defined in: index.ts:612

Deploys a Splitter Proxy contract that splits both principal and rewards.

Unlike Client.createObolRewardsSplit, this method does not deploy an OWR – the splitter address is used as both withdrawal_address and fee_recipient_address.

  • Requires a signer with ETH to pay deployment gas.
  • Sends an on-chain transaction if the splitter is not already deployed (irreversible).
  • Without a controllerAddress (an immutable split), if the predicted splitter is already deployed, returns the existing address without sending a transaction (idempotent). With one (a mutable split), a new splitter is deployed on every call.
  • Automatically appends the Obol RAF recipient.
  • Only supported on Mainnet (1) and Hoodi (560048).

Parameters​

ParameterTypeDescription
totalSplitPayloadTotalSplitPayloadConfiguration for the splitter deployment.

Returns​

Promise<ClusterValidator>

The splitter address as both withdrawal_address and fee_recipient_address.

Throws​

If no signer was provided.

Throws​

If the signer is connected to a different chain.

Throws​

If the chain does not support splitters.

Throws​

If required on-chain factory contracts are unavailable.

Example​

const { withdrawal_address, fee_recipient_address } =
  await client.createObolTotalSplit({
    splitRecipients: [
      { account: "0xOperator1...", percentAllocation: 50 },
      { account: "0xOperator2...", percentAllocation: 49.9 },
    ],
  });
// withdrawal_address === fee_recipient_address (same splitter)

Deprecated​

For new clusters use ObolSplits.createValidatorManagerAndTotalSplit. A splitter as withdrawal address cannot make EIP-7002 withdrawal requests, so getting the stake back depends on pre-signed exits. Existing splitters are unaffected.

createClusterDefinition()​

createClusterDefinition(newCluster, version?): Promise<string>

Defined in: index.ts:783

Creates a new cluster definition and registers it with the Obol API.

A cluster definition describes the operators, validators, and configuration for a Distributed Key Generation (DKG) ceremony. After creation, each operator must call Client.acceptClusterDefinition to join.

  • Requires Client.acceptObolLatestTermsAndConditions to have been called first.
  • Requires a signer.
  • The config_hash returned is the unique identifier for this cluster.
  • Threshold is automatically set to ceil(2/3 * operators.length).
  • Creating a duplicate cluster throws a ConflictError.

Parameters​

ParameterTypeDefault valueDescription
newClusterClusterPayloadundefinedThe cluster configuration payload.
versionstringCONFIG_VERSIONDefinition version. Defaults to CONFIG_VERSION; must be one of SUPPORTED_DEFINITION_VERSIONS. Pass an earlier version such as 'v1.10.0' for DKG nodes running a charon release without the latest schema.

Returns​

Promise<string>

The config_hash string that uniquely identifies this cluster definition.

Throws​

If no signer was provided.

Throws​

If version is not supported.

Throws​

If the payload fails validation (unknown fields, fewer than 4 operators, invalid or duplicate addresses, zero withdrawal or fee recipient address).

Throws​

If the signer is connected to a different chain.

Throws​

If an identical cluster definition already exists.

Example​

const configHash = await client.createClusterDefinition({
  name: "my-dvt-cluster",
  operators: [{ address: "0xOp1..." }, { address: "0xOp2..." }],
  validators: [{
    fee_recipient_address: "0xFeeRecipient...",
    withdrawal_address: "0xWithdrawal...",
  }],
});
console.log("Cluster created:", configHash);

acceptClusterDefinition()​

acceptClusterDefinition(operatorPayload, configHash): Promise<ClusterDefinition>

Defined in: index.ts:896

Accepts (joins) an existing cluster definition as an operator.

Each operator in the cluster must call this method with their ENR and the cluster's config_hash to signal readiness for the DKG ceremony.

Before signing, the definition is fetched and verified locally: the returned config_hash equals configHash, the config_hash recomputed from the definition's contents matches, and the definition's fork_version matches this client's chain. The signer's address must be one of the definition's operators. Integrators should show the user the definition's withdrawal and fee recipient addresses before calling this method.

  • Requires a signer (the operator's address is derived from it).
  • Signs two EIP-712 messages: one for the config hash, one for the ENR.
  • If this operator has already accepted with the same ENR, the current definition is returned and nothing is signed.

Parameters​

ParameterTypeDescription
operatorPayloadOperatorPayloadOperator data. Must include enr (Ethereum Node Record). version is optional and defaults to the definition's version; if given, it must match it.
configHashstringThe config_hash returned by Client.createClusterDefinition.

Returns​

Promise<ClusterDefinition>

The updated cluster definition with the operator's acceptance recorded.

Throws​

If no signer was provided.

Throws​

If configHash is not a 0x-prefixed 32-byte hex string.

Throws​

If the signer is connected to a different chain.

Throws​

If the definition fails verification, its version is below MIN_SUPPORTED_CLUSTER_VERSION, or operatorPayload.version differs from the definition's version.

Throws​

If the operator payload is invalid.

Throws​

If the signer is not an operator in the definition.

Example​

const updatedDef = await client.acceptClusterDefinition(
  { enr: "enr:-LK4Q..." },
  configHash,
);

getDepositData()​

getDepositData(lockHash, __namedParameters?): Promise<LockDepositData>

Defined in: index.ts:1143

Fetches a cluster lock by lock hash and returns its deposit data as payloads for EOA.deposit / ObolSplits.deposit (amount in wei, hex fields 0x-prefixed).

By default the lock is fully validated first (validateClusterLock: operator signatures, lock hash, every deposit signature). This is CPU-bound and can take from seconds to about a minute for locks with hundreds of validators; pass verify: false only if the lock was already validated. The lock's fork version must match this client's chain.

Locks from v1.8.0 carry partial_deposit_data, which can hold several deposit amounts per validator (e.g. 1 ETH and 32 ETH). When there is more than one, pass amount (wei) to choose, or read depositsByAmount; deposits is then only set for the chosen amount. Older locks with a single deposit_data are supported.

This is a read-only API call – no signer is required.

Parameters​

ParameterTypeDescription
lockHashstringThe lock_hash of the cluster lock.
__namedParametersGetDepositDataOptions-

Returns​

Promise<LockDepositData>

The lock hash, the available amounts, deposits grouped by amount, and deposits for the chosen (or only) amount.

Throws​

If the lock is not found, fails validation, was created for another chain, has missing/malformed deposit data, or amount is not available for every validator.

Example​

const { deposits } = await client.getDepositData(lockHash, {
  amount: "32000000000000000000",
});
await client.eoa.deposit({ deposits: deposits! });
